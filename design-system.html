Building a design system in Blazor

Every team had their own version of buttons, tables and forms, so nothing looked or behaved the same and devs were rebuilding the same things over and over. For users, that meant a fragmented experience. Someone moving between picking, packing and returns had to learn new patterns in every app, which slowed them down and made mistakes more likely. I saw this as the biggest problem to fix, so I proposed building a design system straight in Blazor, which is what our teams already use. Rather than handing over Figma files to be translated into code, the components were ready to drop straight into projects.

I built the first version on my own in VS Code using GitHub Copilot. It was a bit of a bet on AI, but it let me move much faster than I could have otherwise, and I learnt a lot about how components actually behave in code. That made handing things over to the dev teams much smoother.

As the only designer across nine teams, I couldn’t be in every conversation or design every screen myself. The design system is how I manage that. Teams can build most screens straight from the components and patterns, with a lot less input from me, and users get the same experience wherever they are. That frees up my time for the trickier problems, new patterns and user testing, rather than redrawing the same table for the ninth time.

One designer, nine teams: the system lets teams build screens with less of my direct input

Once the basics were in place, I set up a design system team of 10 developers from across the nine product teams. I already had good relationships with these teams, which made it work really well. Each area had someone championing it, we shared ownership, and the system was shaped by the people using it rather than forced on them.

I also built a component playground, so people like our Product Owners could mock up ideas with real components without needing Figma or a developer. It cut out a lot of back and forth early on and got people thinking about design much sooner.

Palettes covers the foundations too, so things like colours, theming and typography all live in one place. Before this, colours were picked by eye and every app had its own slightly different shade of everything. Now each colour is a named token with its light and dark values side by side, so devs never have to guess a hex code. Everyone’s starting from the same base, and there’s a light and dark mode built in, which matters when some of our users are in a bright office and others are on a dim warehouse floor.

Theming, with every colour token and its light and dark values

Spacing was a big one for us. Our screens are packed with data, so keeping margins and padding consistent is really what stops them feeling crowded. It’s one of those things nobody notices when it’s right, but you can tell straight away when it’s wrong. I showed it on real screens rather than just listing numbers, so it was easy to see how it all fits together, and it also covers how layouts should adapt across screen sizes, from big monitors in the office down to smaller devices out on the floor.

Spacing guidance laid over a real dashboard

Every component comes with live examples and the code to go with them, so devs can copy it straight into their projects. The examples cover the different ways a component can be used, like alerts that can be closed or ones with an action attached, so teams can see what’s already there before building something new. There’s a shared icon set too, so the same action always looks the same wherever you are. It sounds small, but when someone moves between apps all day, things like an edit or export icon being in the same place and looking the same really adds up.

Alert components with code, and the shared icon set

It isn’t just a set of components. Each one comes with guidance on when and how to use it, so teams can make good decisions on their own. Notifications are a good example. We put together a simple decision flow to help teams choose between a dialog, an alert or a snackbar, depending on how much attention the user needs to give.

Guidance for choosing the right notification component

Championing AI across the design team

Outside of my own work, I’ve pushed for AI to be used more across the team. I’ve run presentations on how to bring AI into design workflows, where it’s genuinely useful, and how to question what it gives you.

I think being comfortable with AI is quickly becoming a core design skill, so helping the team get started early has been one of the more useful things I’ve done.

Impact

For the first time, all nine product teams are building from the same set of components. The playground has opened that up to people outside of design and development, and a team of ten developers now looks after the system and keeps it growing. It’s made a real difference to delivery too, with teams seeing up to a 50% reduction in story estimates now they’re building from ready made components.

Reflections

Building the system on my own first, then handing it over to a team of ten, sums up how I like to work. Start small, test it quickly, then put the structure in place to make it last.
